## 1. Avoiding the `tool_call_id` 400 error

A `400 Bad Request` is raised when a message history is malformed. The two causes:

1. A `role: "tool"` message is missing a non-empty string `tool_call_id`, **or**
2. An assistant message containing `tool_calls` is not followed by a matching
   `role: "tool"` response for **every** `tool_call_id`.

### Rules

- **Never emit a tool call without producing its response.** Every entry in the
  assistant's `tool_calls` array must be answered by exactly one tool result.
- **One response per call, IDs must match exactly.** The `tool_call_id` on the
  tool result must be a non-empty string that string-matches the `id` from the
  assistant's `tool_calls` entry. Never `null`, never blank, never truncated.
- **Keep strict ordering.** Immediately after an assistant message with
  `tool_calls`, place the `role: "tool"` messages — before any new `user` or
  `assistant` turn.
- **No orphaned or dangling calls.** If you requested N tool calls in one turn,
  send back N tool results. Do not drop one because it failed or returned empty.
- **Empty/failed results still need an ID.** If a tool errors or returns nothing,
  still return a `role: "tool"` message carrying the correct `tool_call_id` and a
  short error string as its content.
- **Do not fabricate IDs.** Only reuse IDs that were actually returned by the
  runtime for the current turn. Never invent or guess a `tool_call_id`.
- **Don't splice histories.** When compacting/trimming conversation state, keep
  assistant `tool_calls` and their `tool` responses as an atomic pair — never
  persist one without the other.
- **Batch parallel calls correctly.** When issuing multiple read-only tool calls
  at once, each one still needs its own distinct, non-empty ID and its own
  matching response.

- If you are unsure whether a response was already recorded, re-check the history
before appending — a duplicate or missing ID is what triggers the 400.

- To avoid the 400 Bad Request error stating that tool messages must include a non-empty string tool_call_id (or that assistant tool calls lack matching responses), ensure every tool call is correctly answered in the conversation history. [1, 2]

- Core Causes & Fixes

- Match Every ID: Every tool_calls item generated by an assistant message must have a corresponding response message with a matching tool_call_id. [1, 2]

- Avoid Orphaned Tool Messages: Do not pass a message with a role of tool unless it directly follows an assistant message that requested that specific tool call. [1]

- No Empty Arrays: Check your message builder or middleware payload. If an assistant message does not use tools, omit the tool_calls field entirely or set it to null instead of sending an empty array [], which strict API providers reject. [1, 2]

- Handle Execution Errors Gracefully: If a tool fails during execution, still return a valid ToolMessage (or equivalent block) containing the error text and the correct tool_call_id rather than dropping the response. [1]
